# 写前规划自动修正与复核

## 决策与边界

规划器产生的任务安排不合格时，应由工具消化检查意见，而不是把创作意见作为接口异常交给作者。修正不能通过关闭审查、增加字数或丢弃伏笔获得表面成功。

本闭环只处理写前的任务单与场景合同，同时服务拆章准备和全书自动模式的即时规划。正文审校的质量债务政策和独立第二读者不变。

- 使用任务显式选择的模型，当前本机为 DeepSeek Flash；不自动切换到 Opus。
- 单章问题在单章内修正；结构化评估要求窗口重排时，范围最多为当前章及同卷后两章。
- 有正文、正在执行或受保护的章节不允许改动，遇到边界收缩窗口，不跨卷扩大。
- 书级设定、人物关键走向、卷目标、章节数量和各章字数预算不变。
- 未单独填写章长的章节继承小说默认章长（旧数据未配置时使用现有导演默认值 2800），并在修复快照中冻结；不能由修复模型扩大预算。
- 每个卡点默认两轮，每轮包括修正和复核；普通继续、刷新、重启都不能重置预算。

## 执行与持久化

`PlanningRepairCoordinator` 负责生成、检查、修正和整体复核；`PlanningRepairStore` 负责快照、候选、并发校验及事务提交。两者位于 `server/src/services/novel/volume/planningRepair`。

初次生成先保存候选，随后检查。局部修正和窗口重排均使用完整原始评估、当前候选、书级约束及窗口两端只读上下文。返回的义务去向记录必须与实际章节安排一致。

逐章结构和语义检查通过之后，还要整体检查职责遗漏、重复、字数负载、伏笔去向、人物状态及章节衔接。写前提交要求明确的 `usable` 和 `safeToSync`，不能只检查旧的全书模式 `canEnterExecution` 放行标志。

候选存入 `VolumePlanVersion` 草稿，任务 `seedPayloadJson.planningRepair` 保存版本化轮次、阶段、候选引用、检查结论、指导意见和调用中的标记；原始快照单独保存在 `planningRepairSnapshot`。无数据库表迁移。

调用前写入阶段及轮次，调用成功后立即保存结果。响应丢失不能假装尚未调用；恢复时显示不确定状态，请作者确认再继续。网络错误保留技术错误类别，不伪装成质量不通过。

全部检查通过后，在事务内激活候选版本、同步受影响的章节合同并失效旧章节计划。提交前重查数据指纹、任务所有权、正文和保护状态。只读范围不能改动，任何并发冲突都不能覆盖较新内容。上层调用识别已提交结果，不再二次覆盖写入。

导演心跳和进度轮询允许独立更新，但不能覆盖规划修正状态、快照和人工授权记录。普通任务写入在事务内读取最新修正记录后合并；待确认或已取消的修正不能被迟到的进度写入重新启动。模型、指导意见或任务所有权的并发变化仍阻止提交。

## 人工介入

两轮不通过、需要突破修改范围或改变受保护方向时，进入 `waiting_approval`，使用 `step_review_required` 和 `pendingManualRecovery`，不跳到正文重规划分支。

在小说的「节奏 / 拆章」源工作区查看规划修复状态、意见及轮次。默认入口是获取 AI 修复建议：AI 根据当前候选、历次评估、书级约束和允许范围提出具体方向，解释调整内容、保留内容与取舍，标出推荐项。新手只需选择方向，不必自己写专业修复提示；自定义指导作为高级选项保留。

获取建议和采用建议是两个独立动作。获取建议会调用模型，但不修改候选、不领取修复预算、不启动导演。建议携带结构化执行方式：修改候选后复核、仅复核原候选、需要源工作区编辑。修改方式追加一轮并先落实指导，避免先审同一旧候选反复卡住；仅复核不修改合同、不增加修复预算，仍不通过则保持暂停。建议不能声称直接批准正文或跳过门禁。涉及受保护设定或超出修改范围时只能展示原因与源工作区操作指引，不能通过一次选择扩大自动修改权限。

执行方式必须与阻塞覆盖声明共同校验。AI 应明确方案能否覆盖全部当前阻塞并列出剩余缺口；只有 complete 且剩余列表为空的方案可直接采用，这仍不是质量门通过。只改措辞、保留主要阻塞属于 partial。仅复核还必须是有证据的 review_disagreement，不能以 creative_tradeoff 将未解问题降为待办。旧建议没有覆盖声明时不能猜测其有效性。

修改方式携带实际受影响章ID，服务器逐次核对授权窗口并继承邻章缺失的字数预算；不从指导自由文本猜修改范围。恢复请求的执行方式、范围和指导共同参与幂等身份，排队失败后必须完整带回这些参数。先重放已保存的付费修复响应，再处理新的明确授权；指导已应用才清除一次性动作标记。未知调用状态保持暂停，不能重复消费。旧建议缺执行方式时只读保留，需显式重新获取才能采用。旧无方式的技术恢复保留历史行为，不自行推断为重写。

运行记录页只展示状态和返回源工作区的入口。修复成功也不改变原任务的运行模式：推进到可开写仍停在可开写边界，不擅自启动全书正文。

## 建议状态与证据复核

- 建议保存在任务种子中，包含调用标识、候选及修复来源指纹。GET 和页面轮询仅读取；建议必须由显式 POST 触发。重复请求合并，失败或进程中断不自动重放付费请求；需作者明确重新获取。关闭该建议调用的传输重试、格式策略切换、备用模型及 JSON 修复，防止一次按钮隐式发出多次请求。
- 后端保存真正的修复指导，采用接口只接受建议与选项标识。不能信任浏览器传来的任意指导文本冒充已审核选项。选择时及重建修复会话的事务内再次核对来源；章节、候选、设定、轮次或执行状态变化后，不可执行旧建议。
- 已授权但尚未成功排队的修复保留原幂等标识和指导。页面优先提供继续该授权或保持暂停，不能覆盖原授权再次领取额度。
- 章节复核同时收到实际书级约束、当前候选、原始计划与只读邻章，不能仅凭候选的来源声明认证因果成立。历史评审是待核实意见，不能替代当前候选证据。
- 复核对上一轮每个问题标注已解决、部分解决、未解决或上下文不足。已解决项必须引用当前候选的准确原文；仍存在的项由程序按该结构化判定保留原标识。模型在另一份问题列表换了名称，不应使已得到的“不通过”结论变成技术异常；程序保留旧未解项及新问题并强制不可通过，不凭名字相似合并、替模型判解决或裁掉问题。引用不存在、检查漏项/重复或已解决与问题列表矛盾仍属于响应合同错误。旧问题只按原边界判断，新发现的另一项问题独立说明，不能无限扩大“尚未解决”的含义。
- 写前评估检查的是已安排且可执行的动作，不要求提供尚未创作的正文。检查动作、获得资源的过程、代价对下一步的影响已明确写在场景卡或任务单中时，不能因另一个字段没有重复写而再次要求同一修复。真正的知识来源、行动条件或结果机制缺口仍必须处理。
- 新建议的完整输出合同、分类值、数组上限与指导总长度须明确进入提示词；只说“按 schema 返回”不足以让非原生结构化输出模型理解全部限制。说明性列表上限与修改范围安全边界分别管理，不能为满足前者静默删掉修改、保留条件或验证依据。
- 技术性的格式失败与创作意见分开。新手只需在源工作区重新获取可用建议或保持暂停，不承担查询服务器字段、判断接口合同的职责。明确收到但不合格的建议保留私有诊断与原始响应，页面显示下一步；旧记录缺少类型化诊断时使用保守的失败说明，不凭历史错误文本猜创作结论。
- 历史 `rejected_response` 不因新版格式校验通过而自动成为已批准规划。安全重放需要请求当时的候选、来源和轮次绑定，并重新通过完整校验；缺少绑定时保持显式恢复边界，不能仅凭当前候选哈希相同就推断历史审查上下文一致。

## 原选节奏冲突与延期承接

原选候选中的钩子策略和开篇原型必须一起提供。若同一候选自带两套章节节奏，应明确来源冲突并检查叙事价值，不能把某个原型序号强制等同当前细化章序。候选生成与修改需保持钩子策略、早期回报和开篇事件链自洽；不要把整卷戏剧事件塞进名为前三章的原型，再在下游稀释。

审查及建议要看实际已存节奏板，不能只因后续章节尚未细化，就宣称后续没有任何安排。只读节奏拍可证明较粗的计划承接，不能证明具体章节合同存在、正文已经发生，或原本要求前三章兑现的回报已准时满足。延期的承接状态由AI结构化判断为完整、部分、缺失或冲突；任意引文非空不等于承接成立。缺口仍需修复，真正改变范围或受保护方向仍需用户确认。

建议与复核必须同时看到实际已存的同卷后续章节路线，不能只提供可修改窗口和紧邻章节。基线与候选的只读视野分开呈现，覆盖范围与省略量明确；读取远章不授予修改权限。已有承接可直接在 contextEvidence 中引用，无需让本章重复抄录相同安排。以“本章没有抄写”为由否定已存在的后续计划，会让新手反复修复同一份有效内容。

证据索引允许由当前输入树证明的等价路径：场景 key 的扁平引用、保留 causality 的引用以及 sceneCards 的实际数组路径。别名逐叶映射且拒绝歧义，仍须核对同一叶值的准确原文。不得用全局近似查找或任意删路径层级掩盖伪造引用。

## 验证与维护

回归测试包括本机第3章职责过载记录、纯候选约束、两轮上限、技术错误、丢失响应、数据并发、事务回滚、恢复授权和接口幂等。真实验收只调用指定章节的规划闭环，不启动导演后台调度器。

后续升级必须保留四项行为：针对检查意见修正、修后严格复核、整体事务提交、持久化的调用预算。不要恢复全书模式在写前绕过语义检查的旧逻辑。

# 2026-09-27 Contract Validation Protection

Planning repair output opts into strict generated-content constraints. The structured parser and post-validator must share the same schema, including the 600-character task sheet limit. Invalid output must enter bounded format repair before application, not silently pass a relaxed schema and fail later. This is not permission to increase chapter word budgets or discard obligations.

A terminal post-validation failure carries a non-enumerable completed response for durable rejected-response history. It is not an approved candidate. Clear the pending operation only for this confirmed response; transport interruptions and persistence failures retain uncertainty safeguards.
