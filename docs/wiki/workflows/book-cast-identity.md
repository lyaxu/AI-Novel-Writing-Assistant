# 整书人物覆盖与候选姓名

## 背景与决定

长篇需要按整书篇幅和故事结构安排人物，但开篇不应一次塞入全部人物。以 AI 的整书覆盖计划为主合同，核心人物先完成详细档案，后续角色按出场阶段补全。六人是单次补档请求的资源边界，不是整书人数上限。

## 规划和持久化

- 手工三套候选与导演单套候选共用生成和持久化入口。上下文读取 Novel 的章数、字数、卷结构及正式人物，不把本批执行范围当全书篇幅。
- 每个方案的 coveragePlan.roles 记录稳定 identityKey、姓名、层级、故事职责和入场阶段；已完成状态由实际保存的档案决定，不能信任模型宣称完成。
- 生成新方案追加保存，不删除原方案及已完成批次。全新替代方案具有独立身份，模型接收既有命名约束，但不承诺跨方案自动识别语义上的同一个人。
- 补档逐人物调用、逐人物事务保存。下一人失败不回滚上一人，重试只补未完成档案；每步刷新最新人物与姓名上下文。
- 同进程同方案补档只允许一个请求运行；CAS和唯一索引保护并发提交。这不是跨进程费用恰好一次保证；崩溃后未知外部结果仍需核对，不自动重试模型。

## 姓名和身份

- 用户在候选源页改名，事务更新姓名、旧名别名、用户锁、关系端点和覆盖计划。模型不能自行写入用户姓名锁。
- 补档期间发生改名时，拒绝旧名档案提交；不靠字符串替换修补AI自由文本。刷新后显式补档读取新姓名。
- 应用候选把正式 Character 与 appliedCharacterId 绑定放在同一事务；后续应用优先该绑定，只补空白资料，不覆盖正式姓名、用户资料或现有关系。
- 已绑定角色的当前姓名是后续上下文权威，旧候选姓名作为明确别名。旧方案不得恢复原名或重复创建同人。
- 人物确认、章节事实与资源同步通过唯一主名或明确绑定别名解析；不按子串、相似称呼或题材推断同一身份。一个称呼对应多人时保留待核对，显式所有者未确定时不能偷偷改成持有人。
- 遗留无身份绑定方案不能仅凭旧status推断安全：本书有正式人物且无可靠对应时，拒绝静默创建或通过候选改名绕过核对。
- 已应用人物的改名入口在角色档案；此能力不批量改写正文。已写正文更名仍需要独立影响预览、明确确认及备份保护。

## 边界和维护

coverage完成不代表人物已出场，补档完成不代表已进入正式库；后者仍由源页应用动作完成。运行记录只展示状态及源页导航。

结构字段由 PostgreSQL/SQLite additive migration 增加，旧NULL身份可保留；迁移不自动合并人物、不删除原记录。模型输出模式、生成器、存储、应用、同步和前端必须一起维护，不能只在界面加输入框。

模块：`characterPrep/{domain,application,infrastructure}`、`characters/identity`、`dynamics/commands/confirmCharacterCandidateIdentity`、人物准备 HTTP 与客户端候选组件。模块README保留更细技术合同。离线身份与迁移测试不代表真实模型或UI验收。

## 旧库接入与加载

旧库可能已有应用表但没有Prisma迁移历史。不能直接运行全量migrate deploy，也不能为了标记完成而伪造历史。对已验证的增量SQL，先在线备份并验证可读/完整性及原表指纹，再在事务中检查前提、应用新增字段/索引并比较所有原字段。用外部回执记录SQL校验和、备份和结果；部分已应用或schema不符应停止核对。web运行模式与desktop自动迁移的入口不同，必须核对实际模式，避免重复执行。

迁移完成、代码推送、服务加载和真实验收是四项独立证据。加载后核对启动提交、源码/共享产物指纹、只读接口及任务人工暂停；历史停止任务不得随服务启动自动恢复。已加载代码未变化时，后续纯文档提交不要求重启。
