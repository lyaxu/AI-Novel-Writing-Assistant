# 决策文档：AI 小说助手重做方案

日期：2026-10-07
状态：**待用户决策**，本文档不写代码
背景：新书测试暴露大量阻塞性缺陷；用户决定重新设计一个自用工具

## 一、事实基础

### 1.1 开源参照物的实测结果（用户实测，非推测）

用户用大伟 AI 小说家 4.0 写完了一部书：
- **50 章章纲顺利生成**
- **第 1、2 章正文完成**
- 用户评价：「文笔有进步、能看」「总体而言比较稳定」

代码侧实测（`resources/backend/src/`，**未压缩源码**）：
- **7,534 行 / 58 个 `.mjs` 文件**
- 最大文件 `server.mjs` 1,548 行
- 架构：扁平模块，**一条直线状态机**，无第二套并行状态机

### 1.2 现有工具的实测结果

| 指标 | 数值 |
|---|---|
| 后端源码 | **371,658 行 / 1,778 文件** |
| `services/novel` | 136 文件 |
| `services/novel/director` | **130 文件** |
| 客户端最大文件 | `NovelEdit.tsx` 2,834 行 |
| 测试 | 335 文件，29 个既有失败 |

三周内用户在**情节重复**上反复受阻，定位出：
1. 放行层把「确认的重复」降级为不可阻断的质量债
2. 合同层用 18 词白名单判断章节边界，5/5 真实书名全部失明
3. 规划修复与主流程两套状态机互不认识，用户被挡在死路上
4. 防重复自述声明校验后不落库，等于没设防
5. 流程无进度反馈、无操作互斥，前一步未完成可点下一步

## 二、核心判断：差距不在代码量，在架构形状

**371,658 行 vs 7,534 行**。差距不是"写得糙"，而是**形状不同**。

竞品用 7,534 行换来"50 章不断"，靠的是四条决策：

| 决策 | 效果 |
|---|---|
| 一次请求写完整章，**永不拼接、永不打补丁** | 从不产生"半章"这个中间状态 |
| 重试固定 2 次写死在代码里，**失败即停** | 没有 `defer_and_continue` 式"带病继续" |
| 全书大纲 + 伏笔表（埋/推/收精确到章）**在写之前冻结** | 重复在结构上不可能发生 |
| 状态机是**单条直线** `steps[]` | 没有两套状态机互踩 |

**代价**：它的文字质量"一般般"。它用文学质量换了架构稳定性。

**这正是新工具的设计靶心：竞品的骨架 + 现有工具的文学质量部件。**

## 三、要保留的现有部件（先分类，再决定）

### 3.1 强烈建议保留（对文笔/可靠性有实质贡献）

| 部件 | 位置 | 为什么值得留 |
|---|---|---|
| **伏笔账本** | `PayoffLedgerItem` + `payoffLedgerSync` 提示词 + `progressEvery/nextProgressChapter` 节奏 | 竞品也有伏笔表（`foreshadow-plan.mjs`），但我们有"埋/推/收"三态 + 到期自动顺延。**这是长篇不掉链子的核心。** |
| **风格引擎（StyleEngine）** | `server/src/services/styleEngine/`，18 文件约 5,000 行 | 竞品**完全没有**。含：风格档案提取、文风契约编译、antiAi 规则库（`DEFAULT_ANTI_AI_RULES` 数据驱动）、风格重写。**对"去 AI 味"是实打实的能力。** |
| **去 AI 味规则库** | `styleEngine/defaults.ts:610+` `DEFAULT_ANTI_AI_RULES` | **数据驱动**（不是硬编码词表），用户可按书增删。竞品没有这套。 |
| **情绪落地规则** | `context/emotionPresence.ts` `CHAPTER_EMOTION_RULES` | 写作/验收/审查/修复四链路共用。直接针对"人物鲜活"。 |
| **排版合同** | `context/typography.ts` | 段间空行、叙述段 40-120 字、说话人换段。**对阅读感立刻见效，成本极低。** |
| **角色硬事实** | `characterHardFacts` | 防止人物行为失真。 |
| **章节义务合同** | `mustHitNow` / `mustPreserve` / `forbiddenCrossings` | 「本章必达项」显式化，避免漏写关键推进。 |
| **提示词注册表 + 版本治理** | `server/src/prompting/`，126 个资产 | 竞品没有。**版本化 + loader 校验 + 语义重试**这套治理是长期可维护的关键。 |
| **写作后审校（acceptance）** | `chapterAcceptance` | 竞品有简版审校，我们有结构化 `progressionChecks` 三维。**值得留，但要做薄。** |

### 3.2 建议重写（保留设计，扔掉实现）

| 部件 | 现状问题 | 处理 |
|---|---|---|
| 伏笔账本同步服务 | 与导演/规划修复深度耦合 | **摘出为独立模块**，只依赖 novelId + chapterOrder，不认识任何任务状态 |
| 情绪/排版/风格上下文 | 走 `chapterLayeredContext` 复杂选择 + 16000 预算裁剪 | **改成简单拼接**：风格契约 + 情绪规则 + 排版规则，直接进 prompt |
| antiAi 规则 | 在 styleEngine 里，但注入链路绕 | **保留数据，简化注入** |

### 3.3 建议直接扔掉

| 部件 | 理由 |
|---|---|
| **规划修复子系统**（`planningRepair/` 全部，约 3,700 行） | 两套状态机互踩的根源。**新工具不该有"第二套状态机"。** |
| **导演运行时大部分编排**（`director/` 130 文件的大部分） | 复杂度换来的不是质量，是卡死。 |
| **词表类判断**（已删的 18 词白名单等） | 违反 AI-first。 |
| **卷级/多线因果 gate** | 早期加，收益不明，故障成本高。**先不做。** |
| **RAG 检索、漫画/短剧/导出模块** | 与"写长篇"主线无关。 |
| **票据式 CAS 治理**（`casSeed` 体系） | 严谨但在单机单用户场景下过度设计。新工具用**单进程串行**即可。 |

## 四、新工具的架构设计

### 4.1 骨架（借鉴竞品）

```
题材库 → 故事想法 → 世界观 → 人物（含改名全局同步）→ 全书大纲
   → 伏笔表（埋/推/收 精确到章）→ 【冻结】
   → 卷大纲 → 章纲（一次生成 N 章，可重生成）→ 【冻结】
   → 逐章写作：一次请求 = 完整一章 → 审校 → 不合格整章重写（≤2 次）
   → 落库 → 下一章
```

**关键：所有"规划"步骤在写作开始前完成并冻结；写作阶段只读不生成。**

### 4.2 状态机（借鉴竞品，采纳其教训）

**单一 `steps[]` 数组 + 游标**，没有第二套状态机：

```ts
type Step = {
  kind: "outline" | "foreshadows" | "volumeOutline" | "chapterList" | "chapter";
  status: "pending" | "running" | "done" | "failed";
  rounds: number;      // 固定 2 次上限
  error?: string;
};
```

规则：
- 一个 step 没 `done`，**下一个 step 的按钮禁用**（这正是你骂的那点）
- 失败 = 失败，不降级、不放行、不记债
- 进度直接从 `steps[]` 推导，**不另设 progress 字段**

### 4.3 数据模型（极简）

```prisma
model Novel      { id, title, genre, premise, worldview, createdAt }
model Character  { id, novelId, name, role, profile, locked }
model Foreshadow { id, novelId, content, plantChapter, advanceChapter, payoffChapter, status }
model Volume     { id, novelId, order, title, promise, summary }
model ChapterPlan { id, volumeId, order, title, summary, protagonistAction, chapterPayoff, taskSheet, scenes }
model Chapter    { id, novelId, order, title, content, wordCount, qualityNotes }
```

**没有**：`VolumePlanVersion`、`NovelWorkflowTask`、`GenerationJob`、`DirectorRunCommand`、
`PlanningRepair`、CAS seed、`QualityReport`/`AuditReport` 双份、`TaskCenterArchive`。

预计 **12-15 张表**（现有约 40+）。

### 4.4 写作上下文（简化的关键）

一次 prompt 拼进去，**不做预算裁剪、不做分层选择**：

```
[风格契约]      ← StyleEngine 编译的文风要求（含 antiAi 规则）
[情绪规则]      ← 4 条，写作/审校共用
[排版规则]      ← 段间空行、段长、说话人换段
[本章任务单]    ← 冻结的 chapterPlan
[前3章正文摘要] ← 每章 200 字，用于承接与避免重复
[已写伏笔状态]  ← 哪些已埋、哪些该推
[本章伏笔指令]  ← 该埋什么、该收什么
```

**对比现状**：`chapterLayeredContext` 16,000 token 预算 + 复杂组选择 + 8 个 context broker。
新方案直接拼，**约 3,000 token**。

### 4.5 防重复（三道，按竞品思路重做）

| 道 | 机制 | 拦截时机 |
|---|---|---|
| 1 | **规划前置**：多章章纲一次生成、冻结后才写 | 结构上不可能 |
| 2 | **相邻声明**：`protagonistAction`/`chapterPayoff` 逐章声明（**这次一定要落库**） | 排章时 |
| 3 | **写作后审校**：与前 3 章摘要 + 全书伏笔表对照，发现重复则**整章重写** | 写完后 |

第 3 道的判据不是词频，是**"这一章有没有做前几章做过的事"**，交给模型判断（符合 AI-first）。

## 五、工作量估算

| 阶段 | 内容 | 预估 |
|---|---|---|
| 0 | 决策确认 + 旧库封存 | 半天 |
| 1 | 数据模型 + 基础 CRUD + 桌面壳 | 3-4 天 |
| 2 | 规划链路（题材→想法→世界观→人物→大纲→伏笔） | 4-5 天 |
| 3 | 风格引擎移植（最大块，5,000 行里有 3,000 行可摘） | 5-7 天 |
| 4 | 写作器（一次成稿 + 审校 + 重写） | 3-4 天 |
| 5 | 界面（**按步骤推进 + 互斥 + 进度可见**） | 4-5 天 |
| 6 | 端到端联调 | 3 天 |

**合计 3-5 周**（每天 4-6 小时投入）。

对比：继续修现有工具 —— **不可预测**。我们已经在这个坑里待了 3 周，
修完一个 bug 又冒三个。而重做是**范围明确的从零构建**。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 重做一半又想抄回现有工具的复杂度 | **明文禁止**：新工具不引入规划修复、多线因果、卷级 gate |
| 风格引擎移植时耦合了旧 Context Broker | 移植时**只摘纯函数**（编译/渲染/规则），不摘注入逻辑 |
| 前 3 章摘要不够长导致仍重复 | 摘要 + 伏笔表 + 全书章纲三层都给；同时第 3 道审校兜底 |
| 质量下降 | 用现有《外卖小道士》第 1、2 章（9,355 字，已修复版）作**回归基准**：新工具必须产出不重于它的正文 |
| 又是"看起来能用，一跑就卡" | **每阶段必须真跑一本新书**，不接受只跑单测 |

## 七、需要你拍板的问题

1. **范围**：先只做"长篇主线"（砍掉短篇/漫画/导出/短剧）？
2. **数据**：旧工具 11 本测试书已全部删除、备份在
   `.codex-run/cleanup-20261007/`。新工具**从空库开始**还是**导入某一本**？
3. **平台**：继续 Electron 桌面版，还是先做纯后端 + 浏览器？
4. **模型接入**：DeepSeek / Kimi / MiniMax / 三方聚合 —— 新工具是否**只接你实际在用的这几个**？
5. **验证标准**：第一本书写多少章算成功？（我建议 **10 章**，足以暴露"重复"和"卡死"，
   又不至于耗太久）

## 八、我的建议

**先做决策，不急着开新窗口写代码。**

理由：这次重做的价值取决于**范围砍得够不够狠**。如果把现有工具的复杂度带进去，
371,658 行会原样复活，只是换了个壳。

具体建议：
- **只做长篇主线**，砍掉全部旁支
- **状态机只留一条直线**
- **上下文直接拼，不做预算裁剪**
- **第一天就把"步骤互斥 + 进度可见"做出来**，因为这是你被坑最惨的地方

确认上面 5 个问题后，再开新窗口按阶段推进。
