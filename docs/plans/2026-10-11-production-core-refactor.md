## 保留、吸收、重做

| 处理 | 内容 | 边界 |
|---|---|---|
| 保留旧版 | 模糊想法、故事候选比较、书级大底、人物关系、卷级走向 | 减少重复生成与重复确认，不砍掉创作能力 |
| 保留旧版 | 用户认可写法、正文 writer、知识库、有效事实与伏笔来源 | 第一阶段不换模型、不重写写法、不整体更换提示词 |
| 保留旧版 | 质量检查、原稿/候选择稿、局部修订、字数预算 | 检查要有证据和阶段范围，不能把假指控喂给修订 |
| 硬保留 | 编辑器稳定实例、本地草稿、刷新恢复、保存清理、离开保护 | 重构不得回归丢稿 |
| 吸收新版 | 简短步骤、可见产物、修订对照及保留原稿、调用记录 | 吸收行为与经验，不整体搬运其不可靠执行链 |
| 重做或收敛 | 生产状态权威、持久化检查点、恢复、版本与并发、前文实际状态 | 先核实现有能力和缺口，不能叠加另一套导演或任务状态机 |
| 不继承新版 | 硬题材模板、近似词判定伏笔事实、保存只在末尾、把章号计划当事实 | 都不能用于保障故事正确性 |

## 目标主链

```text
选择故事 → 准备近期章纲 → 冻结本章执行约定
→ 生成正文并保存 → 审查 → 必要时一次局部修订及复核
→ 选择保留稿 → 提交实际故事状态 → 下一章
```

这不是宣称旧版没有出稿即保存：`chapterRuntimePipeline.ts` 已在审查前保存 drafted 正文，`ChapterExecutionPreparationService` 已有 3—5 章即时路线准备。重点是补齐中断恢复、流式部分稿、入口一致性及多份规划的权威关系。

### 一条执行状态，多个只读投影

- 每章生产绑定任务、输入版本、本章合同、模型/写法快照和操作标识；导演、节奏板、章节页显示同一权威结果，不各自推算“应回到第几步”。
- “已保存”“检查通过”“事实已同步”“导演范围完成”分别记录；质量警告不冒充运行失败。
- 每个完成步骤保存输出及引用。审查失败只恢复审查，状态同步失败只恢复同步，不重新生成已有正文。
- 输出流中的部分文本按未完成草稿持久化；截断不能被标为完成正文。外部调用结果未知要显示不确定，不承诺模型计费恰好一次，不盲目补发。
- 同一任务单一执行所有权；重复点击复用已有执行，过期执行不能覆盖新版本。提交前校验正文/合同版本，人工改稿优先保护。
- 复用现有任务、产物和版本表，先列出现有写入者/恢复者；是否需要字段或表在缺口审计后决定，不先引入新队列平台。
- 旧入口经适配层进入同一章级服务。迁移期明确每个字段唯一写入者，旧路径不得与新路径同时执行同章。

### 规划只服务即将写的内容

- 书级方向、人物关键走向、卷目标作为稳定约束；近期 3—5 章联合安排推进、区别和回报。只冻结正在执行的本章合同，后续未写章节随实际结果受控调整。
- 联合规划的窗口大小不等于自动修复权限：自动改动仍限当前及同卷后两章，已有正文、锁定章节和卷边界缩窗，两轮额度持久化。
- 章纲、任务单、场景卡是一个有效版本的不同细度/视图，不能成为三个互相否定的剧情真源。允许有用细化，不重复从零规划。
- 题材标签是参考，不把“都市+玄幻”锁成单一套路；世界规则由本书设定决定，不默认金手指必有永久代价。
- 计划通过既有结构、语义和窗口复核后才能写；不能为了顺畅跳过质量门禁。
- 不承诺“提前冻结规划就不可能重复”。这是旧实验未证实假设，不是架构公理。

### 故事有意思的保障位置

- 在候选选择与近期规划中看主角主动选择、阻力、行动后果、关系变化、阶段所得和后续期待。少量有差异的故事走向比更多打分表有价值。
- 每章要让读者感到某种变化，但不要求每章必胜、必打架、必反转。平静章也可有关系推进、幽默、期待或有意义的决定。
- 市井细节与细腻心理应影响选择和关系，不用罚款、欠租、流程琐事占满多章。
- 节奏曲线作为可解释的提示，不能仅凭平直曲线阻断写作。文学验收以正文和用户阅读为准。
- 第一阶段只保住已获认可的创作链，不同步调创作参数；后续用固定版本对照检验规划改善。

### 检查与实际状态

- 区分网络/鉴权/额度故障、无效审查回答、有证据的故事问题、可选文风意见。无效审查不是小说不合格，不能据此改正文或改伏笔章号。
- 引文验证保留准确性；可评估稳定证据 ID 与服务端还原原文，不能靠近似字符串证明剧情事实。语义判断仍由结构化 AI 评估。
- 无效审查只允许有界纠正；耗尽后显示“尚未完成审查”，不能伪造通过，也不新增一层审查模型来审查所有审查。
- 正文局部问题按任务质量策略，一次局部修订并复核；没有改善保留原稿，记录质量债。需要结构性重规划或安全/数据完整性错误仍暂停。不得悄悄改变现有 completion-first / quality-first 策略。
- 最终保留稿决定事实增量：地点、物品归属、人物已知信息、关系和伏笔实际进展。计划中的第22章埋设不等于已经埋设，知识库也不等于本书事实。
- 关键事实提取或提交失败时保留正文、停在状态提交步骤，不能悄悄拿旧事实写下一章。计划只调整未写范围，不倒改已写正文或核心方向。

## 分阶段实施与停止条件

| 阶段 | 状态 | 最小交付与验收 |
|---|---|---|
| 1 基线与隔离 | 本窗口完成准备 | 保留两版产物与原始停点；专用分支；登记原有 dirty；明确模型/写法差异与证据缺口 |
| 2 单章可靠链 | 实现与离线验证完成；UI待用户验收 | 复用检查点、保存稿件与步骤、CAS、源页普通恢复和未知结果核对、原任务恢复；148项为前序证据，本輪组合回归见阶段3报告 |
| 3 规划、审查及实际状态收敛 | 实现与离线验证完成；真实运行待验 | 有效合同及派生视图；无效审查暂停且保留稿；实际状态按最终稿提交，前章完成边界后再下一章；原写前门禁/预算保留，受管章旧写入入口受保护 |
| 4 固定版本十章验收 | 操作单已准备，未运行 | 先受控重启旧隔离服务，明确新书/模型/预算；按[操作单](../evals/2026-10-11-ten-chapter-acceptance.md)1→3→5→10章阅读，记录失败与人工干预，不边修边宣称连续十章成功 |

首次执行范围为阶段2；后续用户明确持续目标扩展为完成阶段2收尾、阶段3及十章验收准备。普通实现、离线验证、阶段提交及交接在该范围内；付费验收、服务重启与历史清理不包含在自动执行范围中。

阶段2完成后，先报告恢复证据及未覆盖情况，再开始阶段3；不能在阶段2顺手新增题材库、第二读者、节奏评分器或新版补丁。

## 验证与交付约束

- 开始改动前记录代码指纹、输入、配置和数据副本。历史 18/18 及 typecheck 只覆盖旧最小补丁，不替代新核心回归。
- 默认离线故障注入；UI验收由用户执行，除非另外要求自动浏览器检查。
- 真正模型验收先约定范围和成本；不自动恢复旧导演，不重跑成功调用补日志，不启动整本书。
- 每个阶段独立提交，保留原有三客户端文件和工作台账的未提交改动，不混入阶段提交。后续依仓库规则经 beta 验证，不直接晋级 main，不自动 push。
- 阶段 1 仅内部设计和交接，未刷新发布记录；阶段 2 保存/恢复行为实现需记录用户可见变化。稳定决策见[架构边界](../wiki/architecture/production-core-boundary.md)。
