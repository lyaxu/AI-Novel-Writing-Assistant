# 项目长期上下文

这是本地优化的项目文档，不是 Codex 内置个人记忆。启动入口为仓库 `AGENTS.md`；最新任务事实见 [CURRENT.md](CURRENT.md)。

## 用户真正的目标

- 工具应把模糊想法变成值得作者继续加工的故事原型，而不是只把生产流程填完整。
- 长期目标是跨题材接近 8—9 分的小说框架，优先因果、情节组织、人物与关系、阅读承诺及长线回收，文笔次之。具体书和章节用于发现工具机制问题，不以修好样本书替代通用能力改进。评价尺度和阶段边界见 [质量计划](../plans/novel-framework-quality-program.md)。
- 题材正反样例服务开发评测，不自动混入正常写书提示词；用户特别要求覆盖东方玄幻／修仙和传统武侠。避免把任何题材简化成每章必胜、必反转的固定模板。
- 重视冲突、钩子、实际行动后果、阶段回报和长篇连续性。反对连续多章碎碎念地办一件小事。
- 喜欢普通人、市井人物、细腻心理和生活对白；细腻不能变成拖沓或凑字数。文笔可人工修剪，先保证故事有意思。
- 喜欢以小人物视角讲宏大叙事。先清楚书级大底（最终讲什么、表达什么、以什么选择收尾），再安排卷级推进和正文兑现。时代穿插须服从故事及世界边界，不能让不属于当前时空的物品、认知无由出现。
- 泛化范围包括武侠、东方玄幻/修仙、都市异能、悬疑盗墓、民俗风水、科幻和日常装逼打脸；不能把一种题材的合理要求变成全书种通用禁令。
- 金手指可以直接赠予、突然觉醒、无代价获得；禁止的是未经授权且违背本书规则的临时便利，不是无成本本身。人物关系/人格变化与战力授予须区分，不能强制苦练、牺牲或多章铺垫。
- 人物不能所有时候都像扑克脸。恰当的情绪、有趣的情节、鲜活的人物和清晰的大底共同构成质量目标。情绪应有处境和关系上的原因，影响说话、行动、犹豫、误判及选择，并让对方产生不同反应；不以多写“愤怒”、表情动作或堆心理独白代替。
- 情绪可以克制、压住、嘴硬或前后矛盾，不要求人人激烈外露、每章固定情绪曲线，也不强制每章同时搞笑/热血/泪目。允许讽刺、荒诞、幽默、热血、泪目随故事积累和转折自然发生。
- 发现问题要做通用修复，不给单本测试小说写专用分支，不靠换模型或关闭质量检查掩盖工具问题。
- 不把 AI 检测分数等同于作品质量，也不承诺爆款或签约。
- 样本证明能写出合格的戏，就有验证价值；不要求每本测试书都修到完美。用户明确停止某本时保留证据、停止围绕它反复修复，旧交接中的恢复待办随之失效。换书不是删除旧数据的授权。

## 当前架构方向

以旧版创作能力为基础收敛核心生产链，不另建第三套GUI；新版只作为对照及可借鉴交互。先保证单章持久化与失败恢复，再收敛规划、审查和实际状态，最后固定版本验收连续十章。已批准方案见[核心重构方案](../plans/2026-10-11-production-core-refactor.md)，稳定边界见[生产链边界](../wiki/architecture/production-core-boundary.md)。具体进度只看 CURRENT，不把旧实验和历史台账当自动执行清单。

## 人物能力的明确目标

- 人物阵容须按整书篇幅、题材、卷级结构和情节职责由AI规划；开书核心人物可以少而深入，但不能以固定六人替代长篇角色覆盖。后续人物可分批完善，批次写作范围不能冒充全书规模。此项为主线待完善能力，未因人物库可以自动加人而视为完成。
- 在规划候选人物阶段允许用户直接修改姓名，保留稳定人物身份，后续生成尊重用户改名；需处理别名、称呼和旧方案重应用，避免同人重复入库或旧名复活。已有正文更名应提供影响范围及审阅，未经明确确认不批量改稿。现有档案改名不等于全链改名能力已完成。

## 必须保留的边界

- 章节编辑稳定实例、未保存正文不被后台刷新覆盖、本地草稿恢复、保存清理和离开保护。
- 写前规划修正：当前及同卷后两章、无正文/锁定保护、持久化两轮预算、复核通过后事务提交；普通继续和重启不重置预算。
- 不把正文局部质量债务和必须停下的结构性重规划混为一谈；以任务实际质量策略和结构化结论为准，详见 AGENTS。
- 字数目标及预算仍约束章节，不能靠扩写绕过职责过载。
- 运行记录只读；改变任务的操作在源工作区。删除小说应清理关联残留，但删除仍遵循备份和授权规则。
- 第二读者按需给意见，不自动改正文、不默认阻断生产。模型分工以当前任务和配置为准，不把旧 DeepSeek/Opus/K3 选择写死为永久设置。
- 新提示词进入 Prompt Registry；不以剧情关键词硬编码代替结构化判断。
- 网络故障、输出额度耗尽、结构格式失败、语义质量不合格、页面状态陈旧必须分别诊断。状态读取不得变成模型重试。
- 资源事实同步面向作者应低负担：正文中清楚发生的持有、获得和消耗通常自动记录；只有事实、归属或证据存在真实冲突时才提出具体问题。故事里的危险不等于入账有风险。完整技术字段可供核对，但展示字段不能代替让人看懂问题。用户在首章认可文笔和情节，同时明确反馈资源面板术语难懂；后续验收需单独检查这项体验。
- 用户曾说测试书稿不重要，不代表可以清空密钥、模型设置、知识库、写法或无条件删除数据库。

## 事实与验证

- 实际仓库：`D:/novel/AI-Novel-Writing-Assistant`。外层 `D:/novel` 不是应用分支的依据。
- 最新分支、HEAD、未提交内容、服务端口和任务编号只在 CURRENT/快照记录，接手需重新核验。
- `server/dev.db` 是常规本地数据库位置，但隔离运行可覆盖数据源；必须按实际进程/启动记录核对，不把默认路径当运行事实。备份要考虑 WAL/SHM，一般复制单文件不等于一致性备份。
- 不只看日志宣称 UI 修好了；接口、持久化状态和用户页面要核对。离线模拟、用户实测、完整回归分开报告。
- 阅读评价须读实际正文，并区分情节推进、人物选择、语言表现与连续性漏项。流程顺畅、模型自评分、局部代码回归均不能替代文学判断；正面样本也保留失败记录和缺点，不用它反推所有机制已验证。
- 引文可定位还需核验它是否支持结论：计划、猜测、人物声称与实际发生分开；行动者、时序和持有状态都可能错。修复指令本身也要有真实前提，不能引入未持有物件或未发生事件。
- 补丁回执须结合最终选稿判断，候选声称patched不等于原稿保留后问题已修。检查点执行成功、正文保存、章节批准、资产同步、导演范围完成是不同事实；单章生成不能替代导演恢复验收。
- [结构化输出与恢复边界](../wiki/workflows/structured-output-budget-recovery.md)。其他模块按仓库 wiki 和模块 README 定位，不把旧聊天当实现证据。
- 新窗口默认先只读接手，汇报目标/分支/未提交项/当前卡点/下一步，避免同一 checkout 两个窗口同时修改。
- 当前工作台账见 [WORK_LEDGER.md](WORK_LEDGER.md)，它记录完成、部分完成、待验证、暂停及取消事项；它不是自动执行清单。关键长期规则见[书级构思](../wiki/workflows/book-story-foundation.md)、[跨章推进](../wiki/workflows/narrative-progression-review.md)、[约束范围与阶段回报](../wiki/workflows/narrative-constraint-scope-and-payoff.md)。
- 新的验收发现、修复结论和用户设想必须接回 CURRENT 与 WORK_LEDGER；专项记录可以单列，但不可成为孤立文档。长期规则写本页或wiki，实时状态写交接，讨论未实施的设想明确标注边界。目前记录的[断线续作与书内创作agent](../plans/2026-10-11-resilient-writing-and-book-agent-ideas.md)等待专项设计，不属于自动执行授权。

## 何时换窗口

用户不介意为深入理解小说、代码和证据消耗较多上下文；真正担心的是换窗口后不能完整接住。不要为了节省上下文省略必要审读或只看摘要。交接重点保留判断理由、历次修复及再次失败、未完成承诺和验收边界，并让新窗口先复述接手情况。日志去重/筛选旨在去掉重复输出，不是降低理解深度。

一个修复或验收闭环完成、没有未决写入或模型调用时，适合更新交接并换窗口。多次重复查找、历史结论矛盾或准备转入另一个子系统时应主动提示；不以压缩次数机械判断。
交接是工程状态转移，不是聊天逐字无损复制。新的用户指令始终优先于历史待办。
