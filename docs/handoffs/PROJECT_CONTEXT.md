# 项目长期上下文

这是本地优化的项目文档，不是 Codex 内置个人记忆。启动入口为仓库 `AGENTS.md`；最新任务事实见 [CURRENT.md](CURRENT.md)。

## 用户真正的目标

- 工具应把模糊想法变成值得作者继续加工的故事原型，而不是只把生产流程填完整。
- 长期目标是跨题材接近 8—9 分的小说框架，优先因果、情节组织、人物与关系、阅读承诺及长线回收，文笔次之。具体书和章节用于发现工具机制问题，不以修好样本书替代通用能力改进。评价尺度和阶段边界见 [质量计划](../plans/novel-framework-quality-program.md)。
- 题材正反样例服务开发评测，不自动混入正常写书提示词；用户特别要求覆盖东方玄幻／修仙和传统武侠。避免把任何题材简化成每章必胜、必反转的固定模板。
- 重视冲突、钩子、实际行动后果、阶段回报和长篇连续性。反对连续多章碎碎念地办一件小事。
- 喜欢普通人、市井人物、细腻心理和生活对白；细腻不能变成拖沓或凑字数。文笔可人工修剪，先保证故事有意思。
- 发现问题要做通用修复，不给单本测试小说写专用分支，不靠换模型或关闭质量检查掩盖工具问题。
- 不把 AI 检测分数等同于作品质量，也不承诺爆款或签约。

## 必须保留的边界

- 章节编辑稳定实例、未保存正文不被后台刷新覆盖、本地草稿恢复、保存清理和离开保护。
- 写前规划修正：当前及同卷后两章、无正文/锁定保护、持久化两轮预算、复核通过后事务提交；普通继续和重启不重置预算。
- 不把正文局部质量债务和必须停下的结构性重规划混为一谈；以任务实际质量策略和结构化结论为准，详见 AGENTS。
- 字数目标及预算仍约束章节，不能靠扩写绕过职责过载。
- 运行记录只读；改变任务的操作在源工作区。删除小说应清理关联残留，但删除仍遵循备份和授权规则。
- 第二读者按需给意见，不自动改正文、不默认阻断生产。模型分工以当前任务和配置为准，不把旧 DeepSeek/Opus/K3 选择写死为永久设置。
- 新提示词进入 Prompt Registry；不以剧情关键词硬编码代替结构化判断。
- 网络故障、输出额度耗尽、结构格式失败、语义质量不合格、页面状态陈旧必须分别诊断。状态读取不得变成模型重试。
- 用户曾说测试书稿不重要，不代表可以清空密钥、模型设置、知识库、写法或无条件删除数据库。

## 事实与验证

- 实际仓库：`D:/novel/AI-Novel-Writing-Assistant`。外层 `D:/novel` 不是应用分支的依据。
- 最新分支、HEAD、未提交内容、服务端口和任务编号只在 CURRENT/快照记录，接手需重新核验。
- `server/dev.db` 是本地运行数据库；备份要考虑 WAL/SHM，一般复制单文件不等于一致性备份。
- 不只看日志宣称 UI 修好了；接口、持久化状态和用户页面要核对。离线模拟、用户实测、完整回归分开报告。
- [结构化输出与恢复边界](../wiki/workflows/structured-output-budget-recovery.md)。其他模块按仓库 wiki 和模块 README 定位，不把旧聊天当实现证据。
- 新窗口默认先只读接手，汇报目标/分支/未提交项/当前卡点/下一步，避免同一 checkout 两个窗口同时修改。

## 何时换窗口

一个修复或验收闭环完成、没有未决写入或模型调用时，适合更新交接并换窗口。多次重复查找、历史结论矛盾或准备转入另一个子系统时应主动提示；不以压缩次数机械判断。
交接是工程状态转移，不是聊天逐字无损复制。新的用户指令始终优先于历史待办。
