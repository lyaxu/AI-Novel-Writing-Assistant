## 二、它为什么能连跑 30 章不卡：四条关键决策

### 决策 1｜一次请求写完整章，**永不拼接、永不打补丁**

`whole-chapter.mjs:7` 顶部注释就是设计原则：

> `// One response is one complete chapter. Never apply patches or join responses.`

提示词里反复强调：
- 「一次返回完整本章正文，不输出章名、计划、解释、补丁或单独片段」
- 「禁止把多个版本拼接，禁止接写截断稿」
- 「重复事件不能用于补足字数；同一场调查、发现、离场只能发生一次」

**截断了怎么办？整章重写，绝不续写**（`tasks.mjs:1164`）：

```js
// Discard partial output. Retry the complete request, never continue a fragment.
work.truncations = (work.truncations||0) + 1;
if (work.truncations >= 2) fail('模型连续返回不完整章稿，已暂停…', 502);
```

**对你的意义**：你今天遇到的 8192 输出上限、整章改写候选、`applyChapterPatchRepairPlan` 补丁守卫、Q27 的"章节交接 CAS 误判"——**这一整串问题在这套架构里根本不存在**。因为它从不产生"半章"这个中间状态，也就从不需要去判断"半章算不算完成、要不要续"。

### 决策 2｜重试次数是**固定的 2 次**，写进代码，不是运行时协商出来的

```js
for (let attempt = 0; attempt < 2; attempt++) { … }   // tasks.mjs:521
if (work.revisions >= (work.revisionLimit || 2)) fail('本章经两轮整章修订仍未通过…', 422);
```

失败就是失败，**不降级、不记债、不放行**。没有 `defer_and_continue` 这种"记一笔然后继续"的概念。

**对你的意义**：你今天花在 `defer_and_continue` 上的所有痛苦（误判、锁、孤儿标记、恢复死路），根源是**"允许带病继续"这个设计**。它没有这个概念，所以它不可能被它绊住。

### 决策 3｜规划是一次性、静态、确认后冻结的

作者视频原话（07:00 附近）：

> 「写这些正文的内容，它主要就是文笔而已。但是整个故事最精彩的这些东西，
> 都是用这个**章纲**来去约束、来去告诉 AI 将来要怎么走。」

流程是：**题材 → 想法 → 世界观 → 人设 → 全书大纲 → 伏笔（埋/推/收，精确到章）→ 校验 → 第一卷大纲 → 逐章**。

- 全书大纲和伏笔**在写正文之前就全部确定**
- 伏笔精确到「第几章埋设 / 第几章推进 / 第几章回收」
- **生成后可以人工改，改完就冻结**，写作阶段只读

**对你的意义**：你今天查到的第 2 章重复第 1 章，本质是"排章时看不到已写正文"。它**结构上不会发生**，因为章纲在开写前就全部定死了，写正文时只读不生成。它不是"检测到了重复"，而是"根本不存在能重复的机会"。

### 决策 4｜状态机是**一条直线**，不是一张网

`tasks.mjs` 的主循环：

```js
while (!signal.aborted) {
  const step = task.steps[task.cursor];   // 顺序推进
  if (task.cursor >= task.steps.length) { task.status = "completed"; break; }
  …
  task.cursor++;
}
```

- `steps` 是一个**数组**，游标单调前进
- 每个 step 只有 `waiting / running / failed / paused` 四种状态
- 没有"规划修复会话"这种**与主流程并行的第二套状态机**

**对你的意义**：你今天卡死的根因是——**主流程（自动导演）和规划修复（另一套 8 状态机 + CAS + 锁 + 预算）两套状态机互相踩**。`waiting_confirmation` 只有规划修复那一套认识它，主流程不认识，于是把用户挡在门外还只给一句 409。

它没有第二套状态机，所以不会有这个问题。

## 五、我建议的优先级（先治本，再补功能）

### 第一优先｜把"规划"从"写作过程中"提前到"写作之前"

**这是唯一能根治"情节重复"的改法。**

你现在是：`节奏段 → 逐章生成章节合同 → 写正文 → 验收 → 再生成下一章合同`

所以第 2 章的合同是在**第 1 章写完之后**才生成的——它虽然能拿到第 1 章正文（我验证过 `written_evidence` 确实在上下文里），但模型仍然会重复，因为**合同本身就是在重复的正文面前生成的**。

它不是：`题材 → 人设 → 全书大纲 → 全书伏笔表（埋/推/收精确到章）→ 冻结 → 逐章写作（只读）`

**在第二种结构下，第 2 章的合同在第 1 章写之前就定死了，重复在物理上不可能发生。**

### 第二优先｜砍掉 `defer_and_continue` 对"内容不成立"的放行

你今天 5 次卡死，`defer_and_continue` 贡献了至少 3 次。它是 AGENTS.md 里的 completion-first 策略，但**那个策略适合"文笔不够好"，不适合"这一章把上一章重演了一遍"**。

### 第三优先｜单一状态机，或让主流程认识规划修复的状态

今天那句 409 的死路，本质是两层状态机互不认识。

### 第四优先｜人物改名全局同步（低成本高感知）

## 六、必须说清楚的三件事

1. **不要整体照搬。** 它 7,534 行、文字质量"一般般"（你自己的评价），说明它**用架构稳定性换了文学质量**。你的工具在文学质量门禁上做得更多。这不是谁更强，是取舍不同。

2. **它的"不卡"部分来自功能更少。** 它没有多线因果、卷级 gate、跨章承诺对账、风格引擎这些你有的东西。30 章不卡，部分原因是它不需要处理你那些复杂度。**但"一次成稿 + 失败即停 + 规划前置"这三条是可以单独摘出来用的。**

3. **我没有做这些事**：没有破解授权、没有提取他的 API 密钥、没有把他的代码搬进你的项目。我读的是他随安装包分发的未压缩源码，研究的是架构决策。你的顾虑（不会外传、不用于售卖）我已记下，这不影响我给出判断。
