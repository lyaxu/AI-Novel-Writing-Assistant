# 写前规划修复模块

`PlanningRepairCoordinator` 负责候选修正、章节复核、窗口复核与通过后提交；`PlanningRepairStore` 负责持久化及来源一致性。`domain/` 内的历史投影不调用模型、不写数据库，也不决定语义问题是否解决。

## 执行身份与进度状态

会话身份和事务写入条件分别管理。导演在同一次执行中会随批次进度切换 queued/running，此切换不改变候选、授权或执行者，不能单独使已打开的修复会话失效。会话身份保留任务/小说/工作区归属、attemptCount、startedAt、取消与人工暂停事实；等待确认、失败、完成、取消、换执行或换授权仍使旧会话失效。

归一化只用于会话身份比较。`casSeed` 仍用事务内刚读取的精确状态、启动时间、执行次数和完整seed作条件，不能用归一化状态写数据库。较新的暂停、取消、候选、来源或授权变化继续阻止保存；不重置轮次或清除待核实调用。

`planningRepairDomain` 仅校验修订范围、引用映射、预算及结构。`obligationMoves.revise` 允许同章显式纠正含错误事实的引用，实现原引用到替换引用的可追溯映射；是否仍兑现同一叙事功能由章节和窗口 AI 复核决定。不能为通过引用集合检查强迫保留错误事实，也不能自动推导旧响应缺失的映射。正文、暂停状态和原修复预算仍由既有保护边界管理。

## 跨轮复核的连续性

只传上一轮未解问题，或按数量截掉较旧已解问题，都会使已解决的问题退出评估器视野，随后可能以新名称重复提出。`domain/reviewIssueHistory` 按问题 ID 折叠当前来源内的完整记录：每个问题只保留首次描述与修复范围，以及最后一次结构化判断。所有已解和未解问题都继续参与复核，不按条数遗忘；同一问题的重复轮次不重复传输，不复制整包历史。

这些历史判断不是事实或准入凭证。评估器必须根据当前候选逐项重新输出 `issueChecks`；原文引用仍由 Prompt 层验证。推翻已解判断需要解释实际退化、新矛盾或旧判断错误，相同缺口沿用原 ID，真正不同的问题仍可提出。代码不使用关键词推断问题等价性，也不自动继承 `resolved`。

逐章复核通过 `previousIssues` 与 `priorIssueDecisions` 接收折叠记录；修复与窗口复核通过共享上下文 `issueHistoryByChapter` 接收相同记录，仅包含当前授权章节。原始评审用于追溯问题范围，不能让修复器忽略后续解决依据而重复修正原始问题。

`evidence_refresh` 是来源重新取证的边界；边界前的旧问题和旧引用不能进入新来源的复核上下文。每章独立投影，不能用邻章解决结论替代本章审查。上下文去重不能丢弃较旧问题或免除对当前完整合同的审查。

准入仍要求章节与窗口复核全部通过。历史投影不改变两轮自动修复预算、用户确认边界、正文保护和事务提交规则。

## 已应用义务账本与本轮引用

`currentObligationReferences` 列出当前候选的真实回收引用，是新修订的来源；`appliedObligationMoves`（兼容字段 `obligationMoves`）只记录与候选一起成功保存的累计映射。未应用模型历史不能作为已应用凭证。新增、追加解释或改变标点导致引用变化时，都需由模型明确给出对应映射；程序不得猜测两句的叙事等价性。

重复的已应用 A→B 可按幂等重放处理，前提是与保存账本吻合且当前候选仍有 B，或有保存账本明确连接到当前终点 C。未知原句、伪造替换、循环或不明确的链不获豁免。幂等只免除历史源 A 必须继续存在的要求；当前 B/C 被删仍须本轮新的显式修订，不能借旧账本吞掉义务。累计账本保留 A→B→C，供窗口 AI 复核与原始基线的叙事职责逐项对照；本轮空账本不清掉历史映射。

## 必达事项修订与完整合同

只改场景而强制继承全部旧 `requiredElements`，会让已被正文否定的事项永远无法修复；自由替换整份清单又会丢失义务。`domain/requiredElementRevisions` 因此只接受模型逐项给出的同章一对一映射：original、replacement、reason、preservedFunction 与落实新要求的 sceneKeys。未列事项保留，空替换、未知来源、重复来源、分叉、循环、吞并及恢复旧实现均拒绝。结构检查不能证明事实成立或职责等价。

场景计划是必达事项的权威来源；候选已有顶层兼容副本时同步更新。协调器把候选与已应用修订账本同次保存，并将当前清单和累计映射送入章节、窗口复核。复核必须检查已写事实、原叙事功能、时限和最终场景是否一致；只改清单或只改场景均不能自动通过。旧模型响应没有显式映射时继续保留清单，不按历史叙述猜测修订。

重放已保存响应支持 A→B→C 链及幂等，但当前终点必须存在。`evidence_refresh` 复核已提交合同，清旧质量结论、保留仍与候选一致的应用账本；来源变化导致候选被丢弃的显式 rebase 才清对应账本。原两轮及调用历史始终保留，耗尽后由源工作区显式追加修复；刷新、普通继续、重启不能续赠预算。

## 原策略恢复的协调职责

导演恢复模块在用户显式确认后可保存 `resume_existing_policy`，仅允许尚有预算的原自动复核/修复策略。协调器先复核保存候选，之后与正常执行共用 `nextPlanningRepairAction` 的预算和用户决定边界，不能因为来自恢复入口而增加一轮或忽略人工决定。`review_existing` 仍只复核，不通过即暂停；`repair_then_review` 是用户另行确认方向后的修复操作。

两个候选恢复模式都拒绝缺失候选，不能悄悄重新生成。技术失败保留已有不确定调用保护，确定不通过可在当前剩余预算内进入修复；调用失败不会转成对旧不可信建议的执行授权。来源变化与任务取消仍由保存和提交 CAS 拦截。

### 初始合同调用预算

正常初始调用通过 `generateInitial(beforeModelCall, recoverySeed?)` 进入；每个模型调用前必须先执行 callback。新 session 用 `initialGenerationAttempts` 持久记录最多两次外层调用，历史未知次数不自动补零。专用初始拒收恢复提供完整 `output` 和 `validationError`，仅调用一次定向纠正；`initialContractCorrection` 在调用前消费该用户授权，不能重新赠送正常两次包。纠正次数不占用或增加候选语义修复轮次；付费后校验拒绝保存完整新响应并形成 settled 暂停，网络未知保留 pendingOperation。只有合法输出保存成真实候选后才能进入原语义和窗口复核。授权恢复证明及 source/job/lease 保护归 director/recovery/planningRepair 管理。

## 容量拆分边界

协调器复核第 0 轮允许旧合同没有容量计划，修复轮次起要求合同携带容量计划；结构性容量
超载（必须兑现项/总字数超预算、场景不足、可延期无承接）会把修复范围扩到当前章及后续两个
未写同卷章节，由规划修复把可延期职责写入后章任务单/场景。`applyPlanningRepairCandidate`
用新的 `capacityPlan` 重建来源章 `requiredElements`，并确定性校验每条 `deferable` 在窗口内
更晚章节确有承接；没有承接就拒绝保存，避免“拆分”变成静默删除职责。已写、锁定与跨卷章节
不可进入窗口；窗口内没有后续可写章节时返回 `requiresUserDecision` 或拒绝保存并提示进入
卷规划修复。容量修复结果写入运行日志与未写章节执行历史。完整规则见
[章节容量门禁](../../../../../../docs/wiki/workflows/chapter-capacity-gate.md)。
