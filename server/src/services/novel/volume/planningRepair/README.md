# 写前规划修复模块

`PlanningRepairCoordinator` 负责候选修正、章节复核、窗口复核与通过后提交；`PlanningRepairStore` 负责持久化及来源一致性。`domain/` 内的历史投影不调用模型、不写数据库，也不决定语义问题是否解决。

`planningRepairDomain` 仅校验修订范围、引用映射、预算及结构。`obligationMoves.revise` 允许同章显式纠正含错误事实的引用，实现原引用到替换引用的可追溯映射；是否仍兑现同一叙事功能由章节和窗口 AI 复核决定。不能为通过引用集合检查强迫保留错误事实，也不能自动推导旧响应缺失的映射。正文、暂停状态和原修复预算仍由既有保护边界管理。

## 跨轮复核的连续性

只传上一轮未解问题，或按数量截掉较旧已解问题，都会使已解决的问题退出评估器视野，随后可能以新名称重复提出。`domain/reviewIssueHistory` 按问题 ID 折叠当前来源内的完整记录：每个问题只保留首次描述与修复范围，以及最后一次结构化判断。所有已解和未解问题都继续参与复核，不按条数遗忘；同一问题的重复轮次不重复传输，不复制整包历史。

这些历史判断不是事实或准入凭证。评估器必须根据当前候选逐项重新输出 `issueChecks`；原文引用仍由 Prompt 层验证。推翻已解判断需要解释实际退化、新矛盾或旧判断错误，相同缺口沿用原 ID，真正不同的问题仍可提出。代码不使用关键词推断问题等价性，也不自动继承 `resolved`。

逐章复核通过 `previousIssues` 与 `priorIssueDecisions` 接收折叠记录；修复与窗口复核通过共享上下文 `issueHistoryByChapter` 接收相同记录，仅包含当前授权章节。原始评审用于追溯问题范围，不能让修复器忽略后续解决依据而重复修正原始问题。

`evidence_refresh` 是来源重新取证的边界；边界前的旧问题和旧引用不能进入新来源的复核上下文。每章独立投影，不能用邻章解决结论替代本章审查。上下文去重不能丢弃较旧问题或免除对当前完整合同的审查。

准入仍要求章节与窗口复核全部通过。历史投影不改变两轮自动修复预算、用户确认边界、正文保护和事务提交规则。
