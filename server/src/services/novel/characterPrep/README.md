# 人物准备边界

人物准备以整书人物覆盖为主合同，开篇核心档案只是首个完成批次。人数、层级和情节职责由 AI 根据小说的目标章数、字数、题材及卷级结构决定；代码只验证结构和身份一致性，不按章数硬编码人数。

- `characterCastGeneration.ts` 为手工三套候选及导演单套候选提供统一上下文和生成入口。书级规模读取 Novel，不能使用导演本批范围；模型回传规模不一致即拒绝保存。
- `domain/characterCastCoverage.ts` 负责身份唯一性、覆盖解析、批次选择。新输出必须有全书覆盖；历史无覆盖方案仍可读取，不伪造已完成覆盖。
- `infrastructure/characterCastRepository.ts` 是初始方案的唯一持久化入口。新方案追加，保留旧候选及用户姓名修改。成功核心档案被标记 completed，其余均 planned，不能信任模型自行宣称档案已完成。
- `application/developCharacterCastBatch.ts` 按已保存 identityKey 逐个完善。每个人物生成后独立事务保存，下一人失败时前项保留；显式重试只处理 planned 身份。最多六人是一次请求的资源边界，不是全书人数上限。没有缺失档案时不发起模型调用。
- 分批提交重新读取最新候选；生成期间用户改名时拒绝提交带旧名的档案，以免自由文本复活旧名；显式再补会用最新姓名生成。姓名、锁和别名以数据库为准，身份漂移也拒绝提交。并发修改由 option.updatedAt 检查及 optionId+identityKey 唯一索引保护。
- `CharacterPreparationService` 保留应用门面。用户从人物源页请求完善，运行记录不能提供变更操作。

全书轻量角色覆盖不意味着人物已经出场，也不代表全部档案完成。新成员完善成功后仍须通过原应用动作进入正式人物库。此能力不改正文、不自动执行旧样本，也不能把离线测试视为模型表现或 UI 验收。

新增持久化字段通过双数据库 additive migration 管理；生成 Prisma client 不等于应用数据库迁移，服务加载前需按实际隔离数据库备份及迁移验证。

## 并发及故障边界

同一服务进程内，同一小说同一候选的补档请求在发起模型调用前互斥，重复请求直接返回进行中提示；不同方案不互相阻塞。成功或失败后释放互斥，不自动重试。每个持久化人物边界后重新读取最新上下文，避免此前缓存的姓名锁覆盖期间发生的修改。

此互斥不是分布式租约，不能保证多进程或进程崩溃未知结果的 exactly-once 调用。已保存档案不会因重启被自动抹掉；尚未确认的模型结果需要先核对状态，不能自动再发调用。完整断线续作和跨进程队列仍需专项设计。
